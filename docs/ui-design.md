# 报告与复测界面设计方案

## 设计目标

报告面向评审与交付；复测面向单条问题的验证与证据核对。两页共用视觉语言，但不混淆历史记录、执行状态与本轮结论。

本方案仅为交互与视觉设计，不触发真实目标请求。

## 简洁优先

- 首屏只保留标题、目标、关键数字、问题清单与一个主要操作。
- 未执行时不展示结果区；没有数据的字段不反复显示「未提供」。
- 复现步骤、长描述与原始证据默认折叠，按需要展开。
- 同一内容只提供一个主要复制入口，HTTP 另外保留完整请求与完整响应复制。
- 不在页面展示内部路径、运行编号、工具原理和长篇操作说明。
- 报告正文避免重复全文与重复问题详情；目录、清单与详情之间建立清楚的阅读顺序。

## 共用视觉规范

- 以中性色面板和细边框建立层级，品牌色仅用于主要操作与当前选中状态。
- 严重度与复测状态各有文字标签，不能仅凭颜色判断。严重度使用红、橙、蓝灰；未复测使用中性灰，已修复使用绿，需人工确认使用琥珀色。
- 页面标题 22–24px，区块标题 15–16px，正文 13–14px，辅助信息 12px。命令、URL、HTTP 正文使用等宽字体。
- 8px 间距体系；主要区块间距 24px，面板内边距 16–24px。表格行高约 48–56px。
- 表格与详情使用细边框和选中背景，不为每项套多层卡片。
- 操作具备焦点态、进行中态和失败重试；窄屏下详情改为上下布局。

## 报告页

### 页面结构

1. 页头：报告名称、目标、评估时间、报告状态；次要操作为复制和下载。
2. 左侧目录：执行摘要、漏洞清单、修复建议、测试覆盖、证据附录。
3. 执行摘要：主要业务风险、严重度分布、优先处理事项。避免只显示漏洞总数。
4. 漏洞清单：编号、标题、严重度、影响资产、验证状态。点击展开选中问题的结构化详情。
5. 详情：影响说明、观察事实、复现步骤、修复建议、验证边界、证据。
6. 测试覆盖：清楚列出已验证、未覆盖与受限项，不把未发现问题写成绝对安全。

### 内容原则

- 严重度不等于确认程度，分别显示。
- 将已确认事实、潜在影响、待验证条件分开叙述。
- 源码公开、正常公共接口、第三方产品使用等现象不自动作为漏洞。
- HTTP 与长命令默认折叠，正文保留证据摘要。完整证据作为附录入口。
- 隐去内部 intent/fact ID、主机文件路径与工具错误日志。

## 复测页

### 页面结构

- 页头：复测标题、目标、选用基线与创建时间。
- 工具栏：搜索、严重度筛选、状态筛选。默认不提供全量执行按钮。
- 左侧问题列表：标题、严重度、本轮状态、最近执行时间。
- 右侧详情：问题摘要、预期修复行为、本轮结果，以及该条的「一键复测」操作。
- 点选与执行分开：选择列表项只切换详情，绝不触发请求。

### 状态机

未复测 → 复测中 → 仍存在 / 已修复 / 需人工确认。

执行失败单独显示，不归为已修复。超时、网络不可达、响应无法解析和规则不匹配均不能证明漏洞已修复。

### 数据包展示规则

- 初始状态不展示数据包正文、证据路径或历史执行结果。
- 只有用户点击该条「一键复测」并完成后，才显示该次运行的数据包查看器。
- 查看器以请求、响应双栏呈现，分别支持 Headers / Body 与复制。
- 多个交换使用序号切换，展示方法、状态码、耗时与时间。
- 显式区分基线历史证据与本轮新证据，不能以历史包充当本轮结果。
- 页面统计仅统计真实执行过的条目，初始为「已复测 0 / 总数」，不展示虚构的「仍存在」总数。
- 再次执行时标记进行中，旧结果不冒充本次结果；结果需关联运行编号。

## 推荐实现顺序

1. 先确定原型的布局与视觉方向。
2. 从真实源代码构建组件，避免继续手工替换打包文件的行号区间。
3. 把页面读取与复测执行分为独立接口；执行由显式用户操作发起。
4. 前端按会话、问题和运行编号隔离状态，处理重复点击、切换会话与迟到响应。
5. 验证初始零执行、单条执行、失败不判修复、仅当前条出现新数据包，以及报告下载与正文一致。
